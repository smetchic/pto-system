# Единая система ПТО · СУ-22

Первая рабочая основа отдельного приложения. Стек: Vite, JavaScript, Supabase Auth/PostgreSQL/Storage, GitHub Pages. Данные не сохраняются в localStorage; там хранится только сессия авторизации Supabase.

## Реализовано

- Вход по почте и паролю, неактивные по умолчанию учётные записи; роли начальника ПТО, инженера ПТО, администратора. Система — внутренний инструмент ПТО: бухгалтерия ею не пользуется, её шаги отмечает ПТО. Тема оформления хранится в профиле.
- Объекты, договоры двух направлений, назначение сотрудников на объекты.
- Периоды «объект × месяц», документы С-2а, С-2б, С-3а, С-29.
- Неизменяемые версии содержания, отдельные указатели рабочей и принятой версии.
- Маршруты комплектов хранятся в базе (`pto_workflow_templates`, `pto_workflow_steps`): процентовка заказчику (акты С-2 + С-3а), процентовка субподрядчика, С-29. Переход и возврат с причиной — одной командой с проверкой роли и условий шага; события только на добавление; принятие бухгалтерией отмечает ПТО (кто принял, подтверждение) — для всего комплекта сразу. Статус документа — шаг его комплекта. Подтверждения — записи о событии; квалифицированная электронная подпись не реализована.
- Закрытые файлы (до 20 МБ), ссылки скачивания действуют 60 секунд.
- Выполнение из принятых версий актов; С-3а повторно не суммируется: СМР с НДС в С-3а — сумма актов комплекта, «к оплате» и накопительные колонки вычисляются (`pto_c3a_report`).
- Договоры: направление и имя контрагента вычисляются, текущая стоимость и срок — по подписанным допсоглашениям (`pto_contract_list`). Оперативная оценка выполнения хранится отдельно (`pto_estimates`).
- Миграции применяются к базе по одной; номер файла совпадает с версией в `supabase_migrations.schema_migrations`, откат каждой — в `supabase/rollback/`.
- Сопоставление входящего субподряда с исходящими актами в ценах предъявления. Себестоимость входящего акта не подменяет эту сумму.
- Реестр с колонками субподрядчиков справа, без колонки «Заказчик»; XLSX и печать.
- Проверка, закрытие и повторное открытие периода с причиной, неизменяемые снимки и журнал событий.
- RLS, запрет прямой записи из браузера, транзакционная команда с проверкой роли, области доступа, ревизии и идентификатора запроса.

Это основа для пилота, а не полная реализация модели из `AGENTS.md`. Пока не реализованы: права через таблицу разрешений (отложено, пока ролей три), части договора, договоры в российских рублях, закупки материалов, количественный расчёт С-29, нормативные печатные бланки, сроки шагов, закрытие организации целиком, отмена ошибочных документов, разовый импорт истории. Не переносите весь документооборот до проверки пилота.

## Локальная проверка

Node.js 24:

```sh
npm ci --ignore-scripts
npm test
npm run build:check
```

Тесты выполняют реальный SQL миграции в PGlite (PostgreSQL WASM). Системные схемы Supabase Auth и Storage в тесте представлены минимальными таблицами. Это проверяет SQL/RLS и бизнес-переходы, но не заменяет проверку живого Supabase Auth/Storage.

Для разработки скопируйте `.env.example` в `.env`, укажите URL отдельного проекта и **publishable key**. Секретные ключи в клиент и git не добавлять.

```sh
npm run dev
```

## Развёртывание

1. Создать отдельный репозиторий `smetchic/pto-system` и отдельный Supabase-проект `pto-system`. Существующий `filimonova` не используется. Организацию, тариф и стоимость подтвердить перед созданием проекта.
2. Применить SQL из `supabase/migrations/` в порядке имён к пустому новому проекту. Схема включает RLS и приватный bucket `pto-documents`. Не применять миграции к базе Филимоновой.
3. В Supabase Authentication отключить Allow new users to sign up и Anonymous Sign-Ins. Локальный `config.toml` не меняет настройки облачного проекта автоматически.
4. Создать первые Auth-учётные записи через панель Supabase. Не пересылать пароли в чате или в git. Первые роли назначаются оператором базы по точным UUID (шаблон ниже); дальнейшее управление — в разделе «Команда». Начальник ПТО и администратор — разные роли; один аккаунт имеет одну роль.
5. Authentication → URL Configuration: Site URL `https://smetchic.github.io/pto-system/`; этот же точный адрес разрешить как redirect URL. Временный localhost разрешать только для разработки.
6. GitHub → Settings → Pages → Source: GitHub Actions. В Settings → Secrets and variables → Actions → Variables добавить `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`. Это публичная конфигурация клиента, не service_role. Настройки уже заданы в `deployment.json` для отдельного проекта ПТО; переменные необязательны и позволяют их переопределить.
7. Отправить код в `main`. Workflow сначала проверит миграцию и сборку, затем опубликует только `dist/`.
8. Проверить live: вход; создание объекта/договора/периода; доступ второго инженера; загрузку и скачивание файла; все переходы документа; XLSX; закрытие/повторное открытие. Выполнить Supabase Security/Performance Advisors после применения миграции.

Первичная активация (UUID берётся из Authentication → Users; не запускать с буквальными заполнителями):

```sql
update public.pto_profiles
set display_name = 'Сергей', role = 'head', active = true
where id = '<UUID_начальника_ПТО>'::uuid;

update public.pto_profiles
set display_name = 'Администратор', role = 'admin', active = true
where id = '<UUID_администратора>'::uuid;
```

Ключи, пароли, учётные записи и реальные документы не включены в репозиторий. Страница GitHub Pages общедоступна, бизнес-данные доступны только после входа и по RLS. Для закрытого исходного репозитория доступность Pages зависит от тарифа GitHub.

## Первое прохождение

Начальник ПТО: «Портфель» → добавить объект → добавить договор с заказчиком → открыть месяц → «Новый акт» (С-2, сумма с НДС) → «Справка С-3а» (СМР считается из актов) → открыть комплект → провести по шагам маршрута до «Принято бухгалтерией», прикладывая сканы. С-29 проходит свой маршрут. Затем «Проверить» и «Закрыть период».

Инженер ведёт документы и комплекты назначенных объектов, но не проверяет и не закрывает месяц. Администратор управляет аккаунтами и повторным открытием, но не редактирует выполнение и не отмечает шаги маршрутов.

## Границы эксплуатации

До ввода реальных данных нужно согласовать маршрут, обязательный комплект по договорам, регламент резервирования и протестировать восстановление базы и файлов. Снимок закрытия — история месячных итогов, а не резервная копия. До пилотной проверки сайт не считается введённым в эксплуатацию.

Справочные документы: [GitHub Pages workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages), [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Auth configuration](https://supabase.com/docs/guides/auth/general-configuration).
